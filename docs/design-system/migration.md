# Measured Workshop migration manifest

Baseline: 2026-11-04. This is the prioritized source manifest for the approved layered migration. `inventory.json` is generated by `node tools/build-kitchen-design-inventory.mjs`; it contains every recursive `public/**/*.css` and `public/**/*.js` file, hashes, references, source families, migration waves, routes, screens, and static class-component references. No timestamp is emitted, so unchanged inputs produce identical bytes.

## Coverage and meaning

The initial generated baseline contains **361 source files: 63 stylesheets and 298 scripts; 48 workshop routes including aliases; 43 screen definitions; 1,575 static class components**. All 361 files have a family assignment (100% source classification). The baseline entry graph reaches 330 files and leaves 31 without a statically detected path from `index.html`. Counts describe static source coverage. They do not establish the number of runtime states or reusable component contracts. Classes found in multiple families receive an `operations` primary family and retain their complete `families` and `sources` arrays. Explicit workshop `steps` and `aliases` supply routes; editor, shelf, and device-width entry modules supply additional shell screen definitions. Route aliases are counted as routes and share a canonical destination; they are not additional screens. The old `factory` router definition remains inventoried even though the router redirects it to the requested catalog section.

Family classification is deterministic from the owning filename and explicit route IDs. Catalog/default/library sources use the `operations` family and **wave 5**, preserving the five-family taxonomy while giving the catalog work its own implementation task. Shared shell and support styles use wave 8; their mixed-screen behavior must be checked at every earlier wave.

The generator scans static relative module imports, CSS imports, and entry HTML references. Computed URLs, arbitrary JavaScript execution, conditional rendering, dynamically assembled classes, and full runtime reachability are outside this source inventory. Source hashes make edited CSS, JS, and entry HTML invalidate the stored inventory check. The generator does not mark a file system-native merely because it is classified or passes the static policy. Feature files start `legacy`; the central stylesheet starts `foundation`. **System-native acceptance is currently zero.** Later acceptance must record family QA evidence and deliberately extend the status manifest; regenerating this initial baseline does not infer acceptance.

## Native styling policy interface

Import `checkFile(path, options)` or `checkSource(source, options)` from `tools/check-kitchen-design-native.mjs`. Results contain `path`, `passed`, `diagnostics`, and `exceptions`. Each diagnostic has file, 1-based line and column, selector, property, exact value, code, and remediation message. Parse errors omit declaration-specific fields. `options.allowlist` accepts an entries array or the allowlist document; omitting it reads `docs/design-system/allowlist.json`. `checkFile` resolves paths against the project root unless `options.root` supplies another root. It also checks referenced `--ks-*` names against that root's foundation definitions when available; `options.tokens` can supply an explicit token-name collection. `checkSource` accepts the same optional collection for isolated fixtures.

The dependency-free CSS scanner understands nested blocks, declarations, comments, strings, and parenthesized functions. It reports malformed/unclosed structures rather than silently skipping them. It is a static styling-policy scanner, not a complete browser CSS grammar validator. JavaScript checks cover literal/template inline `style` attributes and `<style>` blocks, direct `.style.property` and `.style['property']` assignments, literal `.style.setProperty(...)`, and literal `.setAttribute('style', ...)`. Ordinary computed widths/coordinates stay outside semantic policy. Computed semantic assignments and template interpolations need a precise color-data exception. Other programmatic sinks, indirect helpers, encoded HTML, object-style assignment, runtime validity, and selector matching still require code/browser review.

Rules reject raw hex, functional and named colors, arbitrary radii/shadows, raw transition/animation times/easing, suppressed outlines, and focus treatments that deviate from the 3px semantic ring with its 2px offset. Radius checks cover the shorthand plus all four physical and four logical corner longhands. Zero `outline-width` and `outline-style:none` are rejected on ordinary selectors because they can suppress inherited keyboard focus. Named-color checks apply to color-bearing properties and shorthands, so unrelated identifiers such as `grid-area:red` or `font-family:Tan` remain valid. Only central `--ks-*` definitions and the foundation reduced-motion timing reset are exempt. Zero/reset geometry, transparent/currentColor, and system-token contracts remain valid. This checker does not establish contrast ratios, pointer geometry, presence of every required focus/state rule, ARIA equivalence, RTL anchoring, reduced-motion behavior, zoom usability, print fidelity, or visual approval.

```powershell
node tools/build-kitchen-design-inventory.mjs
node tools/check-kitchen-design-inventory.mjs
node tools/check-kitchen-design-native.mjs
node tools/check-kitchen-design-native.mjs public/kitchen-visit-start.css
node tools/check-kitchen-design-native.mjs --json public/kitchen-visit-start.css
```

Without file arguments the native checker runs its focused policy regression tests. With file arguments it audits those sources and exits 1 on violations. The initial legacy feature styles intentionally have findings; the focused self-test passing does not claim they have migrated. The inventory checker compares all current CSS/JS with the generated artifact and fails if it is stale or incomplete.

## Exceptions and compatibility

The Task 2 baseline allowlist was empty. The current register contains exact, explained material, technical, user and print exceptions added during family migration; no legacy UI state is silently approved. Add exact entries only when a family migration establishes the actual data use. Supported categories are `material-swatch`, `technical-visualization`, `user-color`, and `print-data`. Each exception must have an exact relative file, exact selector/sink, exact property and full declaration value, category, and substantive reason. There are no glob waivers. CSS color-data exceptions cannot waive radii, shadows, motion, or focus contracts. JavaScript sinks use `[inline-style]` or `[style-assignment]` as their selector.

Example shape, intentionally not a real-source waiver:

```json
{
  "file": "public/example-materials.css",
  "selector": ".material-swatch[data-material=oak]",
  "property": "background",
  "value": "#bd8b54",
  "category": "material-swatch",
  "reason": "Catalog oak material sample; selection state is indicated separately."
}
```

For computed user color, an exact value such as `${material.color}` in an inline template can be documented; direct computed assignments use the exact right-hand expression. Expression case is preserved: `${material.color}` does not exempt `${material.Color}`. Expression contents retain their whitespace; ordinary CSS values allow harmless repeated-whitespace normalization without lowercasing case-sensitive identifiers. Reasons must explain the domain meaning rather than simply request exclusion. Interactive swatches still need a separate state/boundary and contrast review. Product color data outside style sinks does not need a meaningless per-literal waiver.

Compatibility mappings belong to the owning family migration. This task creates no new legacy aliases. Preserve existing behavior while each family adopts `--ks-*` contracts locally. Before recording acceptance, save the required family QA report, resolve P0–P2 findings, run that family's native-policy audit, and verify navigation into adjacent unmigrated surfaces. Final consolidation owns retiring compatibility mappings and marking accepted coverage.

## Task 8 source consolidation and acceptance boundary

All nineteen operations styles now consume the foundation. The default completion gate audits all current 64 CSS and 298 JavaScript sources at supported styling sinks, including static embedded report/editor CSS. It validates required documentation, exact standalone export token parity, local compatibility-alias documentation, operational state hooks, focus/targets/motion and safe central primitive ownership. Source classification remains 100%; accepted system-native coverage remains zero in the current legacy-status generator. Neither source policy nor this manifest changes accepted status. Final inventory hash regeneration and final full-suite/browser gates remain with integration.

`@layer ks-primitives` contains safe form font inheritance, technical numeral alignment, touch behavior and coarse-pointer defaults. Unlayered feature contracts remain local where selector specificity, route/container resets or technical geometry matter. Existing used local aliases are retained and documented in `foundations.md`; no obsolete unused global palette or broad compatibility waiver was introduced. The self-contained `designExportTokens` string in `kitchen-customer-sheet-style.js` exactly mirrors central `:root`; the completion gate rejects drift. Standalone proposal/change-sheet/drawing-book exports retain an embedded token source and their own print rules.

The native scanner now distinguishes actual HTML style attributes from names like `data-c-style`, parameter defaults and empty inline-style resets. It scans static CSS declaration/template literals and handles the current explicit stylesheet assemblies. Unknown generated stylesheet blocks require a precise technical-data exception. The sole report-scene block exception reuses authored polygon paint in painter order; it does not waive UI styles. Existing measured geometry expressions for `--krs-w`, `--pha-ratio` and `--shc-ratio` are recognized only at their exact file/property/expression contracts; altered values and raw colors remain audited. Simple conditionals with only semantic-token branches are checked branch by branch without executing their conditions.

Run `node tools/check-kitchen-design-complete.mjs` for source completion. Run it with `--acceptance` for the strict acceptance gate, which intentionally fails until explicit QA-backed native statuses, each family browser PASS, final full-suite PASS and zero open P0–P2 findings are recorded. This status mechanism has not been implemented or accepted by changing inventory defaults. See `qa-matrix.md` and `qa-final.md` for the remaining evidence.

## Task 8 review corrections

Three source-review findings were reproduced with failing focused checks before correction. The operational active transform was more specific than its reduced-motion reset; all twelve press translations are now gated by `prefers-reduced-motion:no-preference`, and completion models the actual authored media/specificity/order result instead of merely requiring a reset rule. Muted text is now `#53666c`; the central and embedded export roots were updated together and foundation asserts AA normal-text contrast on canvas, inset, action-soft and complete-soft.

Embedded stylesheet ownership now resolves the full bounded literal/identifier concatenation and checks every assignment and `+=` append. Static fragments are joined and audited as CSS, including decoded JavaScript escapes with source-position mapping. Unknown runtime expressions fail closed instead of inheriting acceptance from a safe first literal. The three review examples (unsafe second literal, runtime suffix and unsafe `+=` literal) are regression cases. Known semantic static concatenation/appends and the existing exact index-generated gallery remain supported; the generated gallery's full literal is audited and only its existing index interpolation is allowed. The explicit technical report-paint exception remains exact. This scanner does not execute JavaScript or claim general runtime data-flow analysis.

Subsequent review added unsafe-append/sink/later-safe-reassignment and conditional-reassignment regressions. A reassignment after declaration now fails ownership closed rather than selecting a final value by source order; the checker cannot prove whether that assignment precedes a given sink in execution or whether its condition runs. Static `+=` expressions remain accumulative and audited. This conservative rule prevents later or conditional safe values from erasing an earlier unsafe candidate, while preserving current legitimate static assemblies.
