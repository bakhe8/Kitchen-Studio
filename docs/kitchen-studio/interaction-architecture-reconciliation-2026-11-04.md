# مصالحة معمارية التفاعل مع المصدر الجاري

التاريخ: ٤ نوفمبر ٢٠٢٦. المرجع: `Kitchen-Studio-Interaction-Architecture.html`. هذه الوثيقة تطابق المواصفة المفاهيمية مع المصدر الجاري في المستودع؛ لا تنقل ادعاءات لقطة المصدر 68 إلى التنفيذ الحالي، ولا تعد اختبار استخدام بشري.

## الخلاصة

البنية الحالية ليست نقطة بداية فارغة. مسارات الرفع والمصمم والصف المصنع والحفظ تتضمن بالفعل هوية مستقرة للكائن، ومعاينة قبل التطبيق، وإلغاء السحب، وتراجعاً، وحراسة النسخة، وفصلاً بين المسودة والحفظ. المصالحة المطلوبة هي توحيد الدلالات والعقد الوسيط، ثم سد فجوات العرض والسلوك، لا إعادة كتابة محركات الهندسة.

أهم تعارض مؤكد في المصدر الجاري: `previewKitchenWidthChange()` و`factoryWidthEditable()` يمنعان تعديل عرض وحدة ذات `locks.width=true` مطلقاً. المواصفة تفرق بين قيد المستخدم الشخصي وبين قيود الموقع أو الجهاز: التعديل الصريح للعرض يجب أن يسمح بتعديل قيد المستخدم نفسه، وأن يبقي العرض مثبتاً بعد النجاح، من دون تحرير حقائق الموقع أو متطلبات الموديل.

## مصفوفة المصالحة

| مجال المواصفة | ما هو قائم الآن | الحالة | المصالحة المطلوبة |
|---|---|---|---|
| قاموس الكائنات OOUX | مشروع/غرفة/جدار/صف/وحدة/جهاز/قراءة/خامة موجودة بهويات فعلية | متحقق جزئياً | توثيق معرفات الكائنات والعلاقات في عقد واحد تستخدمه الواجهات |
| تعبئة الصف ثم تعديل الاستثناء | `fillKitchenRow()` و`planWorkshopRow()` وتخصيصات الصف | متحقق | عدم إنشاء محرك تعبئة جديد في طبقة العرض |
| معاينة تعديل العرض | `previewKitchenWidthChange()` و`describeProposalChange()` | متحقق | تغليف النتيجة في عقد نية/معاينة مشترك |
| السحب والرقم والأزرار | مسار المصمم يدعم السحب والإدخال والضبط الدقيق | متحقق جزئياً | إثبات تكافؤ النتيجة والحافة والسياسة باختبار عقد واحد |
| تعديل قيد العرض الشخصي | يقبل المساران الحيان التعديل الصريح مع بقاء `locks.width=true`؛ تستمر `anchored()` في حماية الجهاز والموديل والموقع | متحقق مصدرياً | بقي تعميم عقد النية واختبار القبول البصري |
| حماية الوحدات المجاورة | الأقفال والأجهزة والمواضع المخصصة لا تُستعار كمانحين | متحقق | إبقاء القاعدة وإظهار سبب الحماية في أثر المعاينة |
| أثر السبب والنتيجة | تغييرات الوحدات، المانحون، القطع والسعر متاحة | متحقق جزئياً | توحيد تمثيل `affectedObjects` و`changedProperties` و`constraintReasons` |
| مصدر القيمة/مرونتها/صلاحيتها | موزعة بين field/defaults/workshop والواجهات | متحقق جزئياً | عارض خاصية موحد لا ينسخ قاموساً موازياً للبيانات |
| استمرار التحديد والكاميرا | المصمم يحفظ الوحدة والوجه وبعض موضع العرض | متحقق جزئياً | اختبار فتح التفاصيل/الداخل/تبديل العرض/العودة واستعادة التركيز |
| إلغاء الإيماءة | `pointercancel` وفقد الالتقاط وblur وEscape مغطاة في عدة مسارات | متحقق | توحيد ترتيب Escape: الإيماءة، ثم الطبقة المؤقتة، دون خروج مزدوج |
| نتيجة متأخرة | بعض المسارات تستخدم epoch وحراسة المصدر | متحقق جزئياً | عقد جلسة موحد يحمل `sessionId/intentId/baseRevision` ويرفض النتيجة القديمة |
| معاملة تراجع واحدة | تعديل الصف والحفظ يمران عبر سجلات المسودة/المشروع | متحقق | اختبار أن العرض والجوار والقفل تعود معاً |
| الحفظ مقابل التطبيق | الواجهات تفرق بين تطبيق المسودة وحفظ المشروع | متحقق جزئياً | حالة حفظ مستقلة مرتبطة بلقطة محددة، خصوصاً التعديل أثناء الحفظ |
| القراءة الصحيحة مع تصميم متعارض | نماذج الرفع والحفظ تسمح بحفظ حقائق الموقع مع مشاكلها | متحقق جزئياً | رحلة قبول 2350 مم مع بقاء التعارض ظاهراً |
| الاعتماد والإفراج | موجودان كسجلات وبوابات منفصلة | متحقق | منع انتقال الاعتماد إلى نسخة جديدة تلقائياً باختبار صريح |
| بديل دون سحب | حقول وأزرار موجودة في المسارات الرئيسية | متحقق جزئياً | جرد كل عملية سحب وإضافة بديل مؤشر أحادي حيث ينقص |
| اللغة البصرية | نظام التصميم المركزي يملك حالات التحديد/المعاينة/التحذير/الخطأ والحركة المخفضة | متحقق | ربط الحالات بعقد التفاعل وعدم استعمال اللون وحده |
| النموذج الأولي 2400/800/400 | المحرك يملك أمثلة قريبة واختبارات تغيير/مانحين | متحقق جزئياً | تثبيت السيناريو كاملاً كاختبار قبول واحد مع التعارض 2500 والتراجع والحفظ |

## القرار المعماري

لا تُنقل قواعد الهندسة إلى الواجهة. تبقى الدوال القائمة مصادر الحقيقة، وتُضاف طبقة تنسيق صغيرة تحوّل مدخلات السحب والرقم والأزرار إلى نية واحدة، ثم تعيد نتيجة معاينة قابلة للعرض:

```text
InteractionIntent {
  sessionId, intentId, baseRevision,
  objectId, property, requestedValue,
  referenceEdge, scope, inputKind,
  explicitUserChange
}

PreviewResult {
  status, candidate, affectedObjects,
  changedProperties, protectedProperties,
  constraintReasons, unresolvedEvidence,
  catalogRevision, measurementRevision,
  effectsStatus
}
```

العقد لا يصبح مخطط تخزين جديداً. هو حد بين واجهة المهمة ومحركات الصف والمقترح والمشروع.

## ترتيب التنفيذ المصالح

1. **منجز مصدرياً:** توحيد دلالة تعديل العرض والتثبيت، مع اختبار الوحدة المقفلة شخصياً واستمرار حماية المانحين والأجهزة.
2. إضافة نية ومعاينة مشتركتين فوق محركات العرض الحالية، ثم إثبات تكافؤ السحب والرقم والأزرار.
3. تنفيذ شريحة 2400/800/400 كاملة: معاينة، أثر، تعارض 2500، إلغاء، تراجع، وحفظ.
4. تثبيت استمرار الهوية والسياق والتركيز بين الرسم والتفاصيل والداخل وأنواع العرض.
5. توحيد حالات المصدر والمرونة والصلاحية والحفظ في مكوّن خاصية واحد.
6. توسيع المصالحة إلى الخامات والأجهزة والاعتماد، ثم إجراء اختبار استخدام منفصل مع فنيين.

## حدود الإثبات

نجاح اختبارات المصدر لا يثبت اكتشاف الإيماءة أو سرعة الفني. نجاح رحلة الواجهة لا يثبت صلاحية وصفة المصنع. يبقى اختبار الاستخدام، واللمس الحقيقي، والتعميم على كل المسارات بوابات مستقلة.
