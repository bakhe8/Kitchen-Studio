# الصيانة وما بعد البيع — تصميم التفاعل وعقد التكامل

## المصدر والكائنات

مشروع الفريق ← إيصال التصنيع ← الوحدة المسلّمة ← محضر الاستلام ← سجل الضمان وبلاغات الخدمة. يعتمد الرسم على فحوص الإيصال الثابتة؛ لا يُستخدم المشروع المحلي بديلًا عنه. لم يوجد سجل ضمان سابق في التطبيق، لذلك تُوثق الشروط صراحةً بمرجع ومزوّد وتاريخي بداية ونهاية ونطاق واستثناءات. غياب السجل يعني «الضمان غير موثّق».

## الحالات والصلاحيات

تبقى حالة تنفيذ الوحدة `accepted` عند كل حدث خدمة. دورة البلاغ مستقلة: `open → reviewed → repaired → closed`. يسمح `service-reopen` بإعادة البلاغ من `repaired` أو `closed` إلى `open` مع سبب ودورة جديدة؛ يبقى الاعتماد السابق في التاريخ.

- `warranty-record`: المالك يوثق شروطًا جديدة، دون تعديل السجل السابق.
- `service-open`: المالك أو المصنع يسجل عنوانًا ووصفًا وأولوية وموضعًا؛ يربط الخادم البلاغ بمحضر قبول الوحدة.
- `service-review`: المالك يوثق التشخيص وقرار التغطية ومرجعه. الخيارات `covered`, `outside`, `goodwill`. التغطية `covered` تحتاج شروطًا موثقة وتاريخ تسجيل الدورة ضمن فترتها، مع تشخيص وقرار صريحين؛ التواريخ وحدها لا تقرر التغطية.
- `service-repair`: المالك أو المصنع يسجل العمل المنفذ ونتيجة إعادة الفحص.
- `service-close`: المالك يوثق موافقة العميل باسمه ومحضر الاعتماد بعد الإصلاح.
- `service-reopen`: المالك أو المصنع يسجل سبب عودة المشكلة؛ تتطلب الدورة الجديدة تشخيصًا واعتمادًا جديدين.

يسمح فتح بلاغ بلا ضمان أو بعد انقضاء الفترة الموثقة. يسجل الخادم نسخة شروط الضمان التي استند إليها قرار التغطية. تعديل الضمان لاحقًا لا يغيّر هذا الدليل السابق. الاعتماد توثيق يسجله المالك؛ لا يوجد دور دخول مستقل للعميل في النظام الحالي.

## عقد API

الأحداث تضاف إلى `/api/jobs` والسجل `studio_job_events` دون ترحيل قاعدة بيانات. كل طلب يحمل `action, unit, expected` ومعرّف طلب ثابت، ويرتبط بالحساب عبر `X-Studio-Subject`. الحقول الخاصة:

```js
// warranty-record
{terms:{reference,provider,startsOn,endsOn,coverage,exclusions}}
// service-open
{ticket:{title,description,priority:'normal'|'urgent',anchor:{kind:'front',x,y} /* or {kind:'check',key} */}}
// service-review
{ticketId,diagnosis,coverage:'covered'|'outside'|'goodwill',reference}
// service-repair
{ticketId,work,verification}
// service-close
{ticketId,customer,note}
// service-reopen
{ticketId,reason}
```

حدود النص: العنوان 120، المرجع 180، المزوّد واسم العميل 140، بقية النصوص 500. الاستثناءات يمكن أن تكون فارغة. تواريخ ISO صحيحة بترتيب نهاية ≥ بداية. لا مدة افتراضية أو ضمان مفترض. موضع البلاغ يستخدم عقد مرساة فحص التسليم نفسه.

كل الأحداث المشتركة تعرّف نطاق الوحدة والبلاغ؛ يظل اسم العميل ومحضر اعتماده الخاص محجوبين عن إسقاط المصنع، وتظهر الحالة وتاريخها. السجلات الفنية وشروط الضمان وقرار التغطية مشتركة. تبقى قواعد الإيصال والبصمة والعضوية والتسلسل وإعادة الطلب والخصوصية السابقة نافذة.

## التفاعل والحفظ

واجهة `maintenance`: وحدات الإيصال، مخطط الوحدة ونقاط البلاغات، قائمة البلاغات، بطاقة محضر التسليم والضمان، ولوحة سياقية للفعل المتاح. النقر على المخطط في وضع البلاغ يضع مرساة مسودة؛ اختيار البلاغ يبرز موضعه ويعرض حالته وتاريخه. توجد بدائل بلوحة المفاتيح وموضع المنتصف وربط البلاغ بفحص محدد.

المسودة مستقلة عن أحداث الورشة، بمفتاح حساب/مشروع/إيصال/وحدة/بلاغ/فعل. تحفظ النص الخام، موضع البلاغ، إصدار الإيصال، تسلسل الوحدة، ومعرف المحاولة. التراجع والإعادة محليان؛ السجلات المعتمدة تراكمية. المسودة القديمة لا تُعاد إلى تسلسل أحدث تلقائيًا. المحاولة غير مؤكدة النتيجة تُعاد بالمعرف والجسم نفسيهما، وإقرار POST مع فشل GET يُظهر استعادة دون إعادة التسجيل.

حالات المسودة: فارغة → تحرير → محفوظة محليًا → إرسال → إقرار → نظيفة؛ فشل التحقق يبقي النص، والتعارض يقفل المسودة للمراجعة. التنقل بين الوحدات والبلاغات والصفحات يحمي التعديلات غير المحفوظة. انتهاء ضمان لا يغلق البلاغ تلقائيًا، ونجاح الإصلاح لا يعني موافقة العميل حتى يُسجل الاعتماد.

## دورة حياة التفاعل

| المحفز والحالة المبدئية | إدخال المستخدم | القاعدة | التغذية الراجعة والحالة المستقرة | الحلقة أو مسار التصحيح |
| --- | --- | --- | --- | --- |
| وحدة مستلمة، بلاغ جديد | النقر على جسم الوحدة أو تحديد فحص | مرساة داخل الجسم أو مفتاح فحص وارد في الإيصال | موضع مسودة ظاهر مع وصف البلاغ مباشرة | تحريك الموضع أو التراجع والإعادة قبل التسجيل |
| مسودة محررة | حفظ المسودة | حفظ محلي مع الحساب والإيصال والوحدة والفعل والتسلسل | بيان حفظ صريح؛ استعادة النص والموضع عند العودة | التعديل ثم الحفظ، أو إلغاء المسودة |
| مسودة صالحة | تسجيل البلاغ | محضر استلام فعلي، هوية وصلاحية وتحقق حقول وتسلسل صحيح | نقطة بلاغ مثبتة وحالة مفتوح | خطأ تحقق يبقي النص؛ تعارض يحتفظ بالمسودة ويقفل إرسالها |
| بلاغ مفتوح | تشخيص وقرار تغطية ومرجع | المالك فقط؛ التغطية المشمولة تحتاج شروطًا موثقة وفترة صحيحة | حالة التشخيص معتمدة ودليل ضمان محفوظ وقت القرار | البلاغ بلا ضمان يستمر بقرار خارج التغطية أو خدمة استثنائية |
| تشخيص معتمد | وصف الإصلاح ونتيجة الفحص | المالك أو المصنع؛ لا تجاوز للحالات | أُصلح وينتظر موافقة العميل | إصلاح غير مقبول يعاد فتحه بسبب مسجل |
| إصلاح مثبت | اسم العميل ومحضر موافقته | المالك فقط؛ لا إغلاق قبل الإصلاح | نقطة مغلقة وسجل قراءة مع محضر العميل | إعادة فتح بسبب جديد تحفظ التاريخ وتبدأ دورة مستقلة |
| إرسال غير محسوم | إعادة المحاولة | نفس معرف الطلب والجسم والهوية، دون إعادة بناء الطلب | النتيجة المحفوظة نفسها دون حدث مكرر | يبقى الاسترداد ظاهرًا بعد تحديث الصفحة والتنقل بين البلاغات |
| حدث أُقرّ لكن تحديث العرض فشل | إعادة تحميل السجل | طلب قراءة فقط | عرض الحالة المؤكدة عند نجاح القراءة | لا يعاد إرسال الحدث الذي أقرّه الخادم |

تغير لون النقطة ووصف الحالة وتأكيد الحفظ متزامنة مع الحالة الفعلية. تظل الوحدة ومرساة البلاغ في موضعهما أثناء انتقال المراحل، وتقتصر الحركة على إشارات التركيز والاختيار، مع احترام تقليل الحركة. أدوات النموذج تظهر للفعل المتاح فقط وتحتفظ بمسار لوحة المفاتيح.

## التحقق

اختبارات مجال وAPI للانتقالات والضمان والنطاق والدور والخصوصية والتزامن؛ اختبارات متحكم للحفظ والتراجع والاستعادة وعزل البلاغات؛ رحلة متصفح فعلية بخادم منفصل على 8767 مع معالجات الإنتاج وحسابات وتخزين اختباريين في الذاكرة. لا تثبت هذه الاختبارات OAuth المنشور أو قبول فنيين/عملاء فعليين.
